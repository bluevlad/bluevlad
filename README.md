Each cycle leaves the platform measurably better than before.

### Inside Each Agent

#### 🔍 QA-Agent — *Inspects every service nightly*

A remote QA PC (Windows) runs Playwright E2E/API across the active service fleet at the late-night slot. Findings are **Git-verified, origin-tagged** (regression / new-feature / external-tech adoption), and committed to GitHub Issues with the `qa-agent` label. RAG quality is evaluated on chatbot endpoints. Verified fixes are auto-closed.

> 🎯 **Operator sees** → labeled Issues with reproduction trace. **Decides** → which to fix this cycle.

#### 🤖 Auto-Tobe-Agent — *Fixes and enhances autonomously*

**Dual-engine** — Claude Code CLI (Opus) for complex multi-layer fixes on hopenvision / AllergyInsight / NewsletterPlatform; an Ollama ReAct loop (qwen2.5-coder:14b) for unmong-main / StandUp at zero cost. Auto-fallback to Claude on local-engine failure. Output is a PR with a fix-compliance footer (Discovery-Method · Root-Cause · Recurrence · Prevention) — the same footer feeds the QA Dashboard's prevention-model dataset, so **every fix becomes training data for the next cycle**.

> 🎯 **Operator sees** → PR with rationale + risk note. **Decides** → merge.

#### 📡 InfraWatcher — *Single pane for the whole fleet*

Real-time Docker telemetry over WebSocket — CPU / memory / health-check / restart counts across the multi-subdomain operations fleet. **Auto-recovery on health-check failure**, time-series analytics for rolling-deploy regression detection, container-action surface (start / stop / restart / logs) gated by Google-OAuth admin. From any browser, the operator can observe and intervene anywhere on the fleet.

> 🎯 **Operator sees** → live state of every container, anywhere. **Decides** → manual intervention only when auto-recovery exhausts retries.

#### ✍️ StandUp — *Weekly synthesis that gets smarter every week*

Pulls from three internal operations sources (LogAnalyzer · GitHub QA issues · Auto-Tobe fix journal) into a canonical event store. **Three-stage local LLM cascade** — `llama3.2:3b` summarizes → `qwen2.5-coder:14b` extracts insight → `EXAONE 3.5` composes Korean prose. Each sent newsletter is re-indexed into a **pgvector self-referencing corpus**, so suggestion quality compounds week-over-week. Every body claim renders as `[REF:url]` back to source. `STANDUP_MODE` for zero-redeploy rollback.

**Roadmap (2026-Q2)**
- *Insight Dashboard* — post-send visibility · topic clustering · HopenVision proposal auto-drafting
- *HopenTechBrief* — daily tech-curation channel, paired with NewsletterPlatform TechBriefing v2
- *Claude session-log federation* — dev-discussion context auto-joined to work-item tracking
- *EXAONE Korean-first cascade* — Stage 3 model decision under 24GB MacBook constraint

> 🎯 **Operator reads** → weekly briefing + daily curation, cited back to actual ops events. **Decides** → which suggestion to act on.

#### 🧬 AllergyInsight RAG — *Knowledge base that learns daily*

Daily ingestion across 10+ sources (PubMed · Semantic Scholar · openFDA · MFDS · Naver/Google News · etc.) into a canonical store with three-stage dedup (URL-canonical + content + MinHash). **Dual-surface** — the same store productizes into the `allergy-insight` newsletter tenant **and** seeds the `/ai/consult` chatbot's per-allergen ChromaDB RAG. Five anonymous public pages (MAST · symptoms · chatbot · drugs · clinical images) with diagnosis-disallowed phrasing, citation + license on every response, and emergency-keyword bypass to 119.

**Roadmap (2026-Q2)**
- *Vertical Insight Framework* — 4-layer domain abstraction; new medical domain attaches via YAML + prompts, zero `core/` changes
- *Source Connector Registry* — pluggable ingestion (Paper / News / Regulatory ABC + PMID/DOI cross-lookup)
- *Strategic Intel* — rule+LLM hypothesis engine validated by abnormal returns + 60-day volume z-score (Wilson CI)
- *Newsletter redesign* — impact-based ordering replacing category buckets (MinHash ≥ 0.90 dedup)

> 🎯 **Operator curates** → corpora, allergens, domain packs. **The platform** → grows vocabulary daily; new verticals attach without touching the core.

> ⏸️ **Phase 5** — clinical B2B on hold pending kit-manufacturer partnership.

#### 📧 NewsletterPlatform — *Multi-tenant delivery, hardened by real incidents*

Four tenants (`allergy-insight` · `standup` · `edufit` · `tech_briefing`) on a shared core with `BaseTenant` abstraction. API-driven collection prevents cross-tenant coupling; a 10-step `TENANT_ONBOARDING.md` checklist replaces the ad-hoc migration that the first tenant went through.

**Roadmap (2026-Q2)** — incident-driven hardening + new tenants
- *Stale-cache admin alert* — 24h cache threshold blocks general send; `stale_admin_alert` send_mode routes to super-admins with banner (prevents dedup-pool pollution)
- *Article-level dedup* — SQL-layer 7-day repeat block via `sent_articles` UNIQUE + URL-length-safe `exclude_ids` POST alias
- *3-tier send slots* — single collect feeds 6:40 / 7:40 / 8:40 slots; shared cache yields 1/3 API-call reduction
- *Subscription-abuse hardening* — Turnstile + IP/email rate-limits + honeypot + role-account/bot-name pattern detection
- *TechBriefing v2 + StandUp Weekly tenants* — Service Profile pattern + Ollama deep analyzer for HopenVision ADOPT / TRIAL / ASSESS / HOLD cards (dual-channel with StandUp HopenTechBrief)
- *F/E/L 3-axis plan* — Freshness ✅ · Efficacy 7-day-window A/B · Learning (👍/👎 feedback UI with HMAC-signed tokens)

> 🎯 **Operator sees** → stale-cache alerts, per-slot statistics, abuse telemetry, tenant-isolated bounce metrics. **Decides** → which tenant to onboard next (the framework now scales to N).

### The HopenVision Evolution Loop — Dual-Channel Tech Adoption

> 🎯 **What makes HopenVision evolve** — two complementary channels feed the same operator (hopenvision developers), one for *discovery*, one for *decision*. The Service Profile (`config/service_profiles/hopenvision.yaml` — stack · known_debt · relevance signals) is the shared ground truth; LLMs on both channels are constrained to this profile to prevent hallucinated module names.

| Channel | Source | LLM Role | Decision Surface |
|---|---|---|---|
| **StandUp HopenTechBrief** | Medium digest + Google / Naver News (trend-broad) | 60-pt stack-fitness gate + Mermaid As-Is/To-Be · PoC code hints | *"Worth exploring?"* — proposals auto-drafted as DevPlan |
| **NewsletterPlatform TechBriefing v2** | GitHub Releases + NVD CVE + Spring / React / Vite / Kotlin official blogs (canonical) | `qwen2.5-coder:14b` 4-section card | *"Adopt today?"* — ADOPT / TRIAL / ASSESS / HOLD with estimated cost |

> **Why two channels?** Discovery and decision pull different sources at different fidelities. Splitting them keeps each channel clean — the trend channel can be noisy and explorational; the decision channel is canonical and signs off with a recommendation grade. The same operator reads both, but the cognitive mode is different.

**Cost**: ₩0 — both channels run on the local Ollama instance shared with Auto-Tobe-Agent (same `host.docker.internal:11434`, same `qwen2.5-coder:14b` weights — no per-channel model duplication). Top-N gating + service-relevance pre-filter skip LLM calls entirely on irrelevant items.

### Tech Foundation

#### Dual-Engine — Claude + Local LLM

Auto-Tobe-Agent's two engines map to project complexity, with automatic fallback.

| | Agent-A (Claude) | Agent-B (Local LLM) |
|---|---|---|
| **Engine** | Claude Code CLI (Opus 4.6) | Ollama ReAct loop (qwen2.5-coder:14b) |
| **Projects** | hopenvision · AllergyInsight · NewsletterPlatform | unmong-main · StandUp |
| **Strength** | Complex multi-layer · 1M token context | Zero-cost · offline · fast for simple fixes |
| **Fallback** | — | Auto-fallback to Claude on failure |

#### Document RAG — Free vs Paid

The same RAG pipeline (ingestion → chunking → embedding → vector DB → hybrid search → LLM synthesis) supports two stacks, selectable per use case.

| | **Free Tier — Gemini** | **Paid Tier — OpenAI + Claude** |
|---|---|---|
| **Repo** | [Google-Gemini-Ai-PipeLine](https://github.com/bluevlad/Google-Gemini-Ai-PipeLine) | DocumetsToAiPipeLine *(private)* |
| **Embedding** | Gemini `text-embedding-004` | OpenAI `text-embedding-3-large` |
| **LLM** | Gemini 2.x Flash | Anthropic Claude 4.x |
| **Vector DB** | ChromaDB | ChromaDB → pgvector |
| **When to Pick** | Fast validation · offline · small | High-precision recall · long context |

#### Local LLM Observability — LLMOps

The fleet's **5 LLM consumers** (StandUp synthesis · AllergyInsight RAG chat + paper translate · Auto-Tobe Agent-B · medium-digest) emit a per-run report through a fire-and-forget SDK (Python + TypeScript, stdlib-only `urllib` / `fetch`, 1s timeout, no retry) into a single PG store. Replaces the port-only health check that InfraWatcher provided — gives a per-model usage / latency / ROI lens the original services had to keep in their own heads.

| Phase | Output | Status |
|---|---|---|
| 1. Skeleton | FastAPI + React + Google OAuth + Ollama (10min) / MLX (1h) inventory pollers | ✅ |
| 2. SDK + ingest | `shared/llmops/` (Py + TS) · 5 consumers wired · `flush()` for short-lived jobs | ✅ |
| 3. Visualization | service ↔ model matrix · pipeline heatmap · corpus growth | 30-day data window |
| 4. Analysis | ROI translation · quality-drift regression | 60-day data window |

> **Design constraint** — fire-and-forget so LLMOps downtime never propagates to producer services. Sunset clause baked in: "if ROI insufficient at 6 months, fold back into InfraWatcher."
